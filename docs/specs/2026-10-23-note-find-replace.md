# 笔记内查找替换

> 2026-10-23。前置：`⌘F` 笔记内查找（早已有，只查不改）。

## 问题

`⌘F` 能定位到匹配项，但改起来还得把光标挪过去手改。日常编辑里「这个词全篇改成那个词」
是最常见的批量操作，没有替换就只能逐个手改，还容易漏。

## 目标

在既有查找条上加替换，**不改变 `⌘F` 的既有心智**：

| 入口 | 行为 |
|---|---|
| `⌘F` | 只打开查找（一行，与原来完全一致） |
| `⌘⌥F` | 打开查找并展开替换行 |
| 查找条右侧替换图标 | 展开 / 收起替换行 |
| 替换框 `Enter` | 替换当前匹配并跳到下一个 |
| 替换框 `⌘Enter` | 替换全部 |

macOS 上 `⌘H` 被系统「隐藏窗口」占用，替换只能挂在 `F` 的 `⌥` 变体上。

## 匹配口径

与既有 `findText` **完全一致**，不新增能力：

- 大小写不敏感（`toLocaleLowerCase` 后比对）；
- 不解析正则，`%` `_` 等就是字面字符；
- **只在单个文本节点内匹配**：`线程` + 加粗的 `池` 不会被当成一个词。
  跨节点命中会牵出标记边界，替换后新文本该继承哪边的样式无从判断 ——
  宁可"找不到"，也不猜。

## 两个编辑器，两套实现

| | 富文本（笔记） | 源码（外部 `.md`） |
|---|---|---|
| 批量替换 | 倒序 `tr.insertText`，一个 transaction | 一次 dispatch 带 `changes` 数组 |
| 撤销粒度 | 一次 | 一次 |
| 单次替换的目标 | 当前高亮那一条，失效则第一条 | `findField.active` 指向那一条 |
| 替换后定位 | 在新文档上重新收集匹配，从替换位置往后找下一个，末尾绕回开头 | 同左 |
| 预览态 | 先 `togglePreview()` 回编辑态 | 先 `switchMode('source')` |

倒序是关键：靠前的匹配偏移不会被打乱，且整体只产生一次撤销 ——
撤销后不会留下"替换到一半"的中间态（e2e 里有专门断言）。

**替换文本按纯文本插入**，不走 `markdownToSlice`：替换框里写 `**粗**` 得到的就是这串字符。
用户要的是改字，不是改样式；真按 Markdown 解析会凭空生成节点，撤销粒度也会碎掉。

## 为什么替换行默认收起

查找条是浮在正文右上角的药丸（`position: absolute`）。常显两行会把高度从 39px 撑到 66px、
压住更多正文，而绝大多数 `⌘F` 只是看一眼。所以默认一行，需要时展开。

## 落点与状态同步

- `App.vue` 维护 `noteReplaceVisible` / `noteReplaceKeyword`，与查找关键词同生命周期：
  关闭查找收起替换行，**切笔记 / 切文件清空替换词** ——
  不清的话换一篇按 `⌘⌥F` 会带着上一篇的替换目标，误点「全部」就是灾难。
- 替换后立刻用返回值回写 `noteFindResult`，否则全部替换完界面还停在 `3/12`。
- 结果提示复用 `showEditorFeedback`（顶部居中药丸）：`已替换 N 处` / `没有可替换的匹配`。
- 正文变更照既有链路走：富文本 `emit('change')` → 自动保存防抖 1.5s；外部文件需 `⌘S` 手写回盘。

## 样式红线

查找条模板从「一层 flex」变成「容器 + 行容器」两层，**子选择器必须跟着改**：

```css
/* ❌ 静默失效：不报错，只是不生效 */
.note-find-bar > input { ... }
/* ✅ 输入框已经下沉到行容器内 */
.note-find-row > input { ... }
```

暗色主题是独立的一段（`html[data-theme="dark"]`），漏改会得到
「浅色正常、深色下输入框发黑」。单测里钉死了这两条。

替换行的按钮是文字按钮，要单独 `width: auto` + `white-space: nowrap`，
否则会继承查找行 27px 的方格尺寸，「全部」两个字会叠在一起。
